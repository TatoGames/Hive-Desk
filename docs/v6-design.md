# HiveDesk v6 설계안: 내 PC에서 시작하는 전용 AI, 3단계 모델과 서버 확장

> 구현 현황은 [`docs/next-design.md`](next-design.md)를 참조하세요. 이 문서는 설계 원문이고, 10장 표에 완료 표시를 덧붙였어요.

작성일: 2026-10-19  
상태: 일부 구현됨(챗-1, 8-1·8-2·8-2b·8-4·8-4b는 v0.7.0~0.7.2에 완료, 나머지는 개발 전). v6는 문서용 가칭이며 실제 릴리스 번호는 별도로 정한다.  
범위: 로컬 AI 실행 → 업무 도구 연결 → 3등급 확장 → 다중 사용자 서버 운영. 첨부된 v5의 이어받기·작업 현황 설계와 연계한다. **기본 AI 챗(14장)을 함께 설계에 넣었다.**

> **방향 정리 (2026-10-19)**: ① 등급은 업무 난이도가 아니라 **PC 성능** 기준이다. ② API 키 연결은 만들지 않는다(유료). ③ 로컬 모델은 **OpenAI 호환 연결**(Ollama·LM Studio 등 로컬 주소)로 붙인다. ④ 서버 운영은 후순위다. ⑤ 로컬 모델은 **먼저 내 PC에서 실측**하고, 맡길지는 **기대 이익**으로 판단한다(5-4). ⑥ 작은 모델은 도구를 알아서 쓰게 하지 않고 **앱이 이끄는 수정 방식**으로 쓴다(4-5). 아래 본문은 이 내용에 맞춰 고쳤다.

> 단계 번호 8-1~8-9는 이미 v0.5.1 작업(자동 검사·검토 절약)에 쓴 이름과 겹친다. 구현할 때는 이 문서의 단계를 "v6 8-x"로 부르고, 챗은 "챗-1~3"으로 부른다.

## 0. 목표

1. 사용자 PC에서 AI를 실행해 외부 구독 사용량이 소진돼도, 로컬 모델이 수행 가능한 업무는 계속 처리한다.
2. 사용자 PC마다 성능 차이가 커서 오래 걸리거나 멈출 수 있다. 그래서 로컬 모델을 **PC 성능에 맞춘 세 등급**(Light / Standard / Advanced, 가칭)으로 나눠, 앱이 PC를 진단해 맞는 등급을 추천한다. 첫 출시는 Standard 하나로 검증하고 나머지를 순차 추가한다.
3. 개발 초기부터 모델 실행과 파일 작업을 분리해, 이후 AI 계산 부분을 서버로 옮길 수 있게 한다.
4. 여러 사용자가 서버를 이용할 때 계정·회사별 자료와 권한을 분리하고, 대기열·사용량·비용을 관리한다.
5. 사용자가 모델 설치 명령이나 개발 용어를 몰라도 설치 → 업무 배정 → 결과 확인을 할 수 있게 한다.
6. **업무를 맡기는 것과 별개로, 모델을 골라 쓰는 기본 AI 챗(대화)을 앱 안에 둔다.** 지금 연결된 CLI로 먼저 만들고, 이후 내 PC AI·서버 AI가 같은 챗에 모델로 더해진다. (14장)

‘한도 걱정 없이’는 외부 구독 서비스의 사용량 한도에 의존하지 않는다는 의미다. PC 메모리·속도·디스크·전력, 모델이 한 번에 읽을 수 있는 양에는 제한이 있다. 서버 상품에는 별도의 사용량·동시 실행 제한을 둔다.

## 1. 지금 상태와 용어

### 1-1. 확인한 현재 기반

이 대화에서 읽은 README와 `adapters.ts`, `runner.ts`, `delegation.ts`, `committee.ts` 기준이다. 전체 코드 감사나 실제 실행 검증은 하지 않았다.

- HiveDesk는 로그인된 외부 AI CLI를 실행하고, 업무·직원·메모리·승인·결과를 관리한다.
- `custom` 어댑터로 직접 지정한 프로그램에 지시를 전달할 수 있다.
- 실행마다 역할·업무·공유 메모리·관련 결과 등을 조합한다.
- 위임·교차 검토·위원회는 여러 번의 AI 실행을 만들 수 있다.
- 기존 체크포인트·변경 비교·권한 관리·작업 기록을 새 실행 방식에서도 재사용할 기반이 있다.

부족한 부분은 로컬 모델 설치·상태 관리, 모델이 요청한 도구를 실행하는 반복 처리, PC 자원 스케줄링, 서버용 인증·격리·과금이다. `custom`에 모델 실행 명령을 넣는 것만으로 파일 작업 에이전트가 완성되지는 않는다.

### 1-2. 모델을 내려받는다는 뜻

| 용어 | 쉬운 설명 |
|---|---|
| 모델 파일 | 다른 개발사가 학습한 결과를 숫자로 저장한 파일. PC에 내려받아 계산에 사용한다. |
| 실행 엔진 | 모델 파일을 읽고 답변을 생성하는 프로그램. 초기 후보는 Ollama다. |
| 에이전트 | 모델의 판단과 파일 읽기·수정·테스트 도구를 연결해 일을 수행하는 구성이다. |
| 직원 | HiveDesk에서 역할·소속·권한·업무를 부여한 자리다. 직원마다 별도 모델 파일이 필요한 것은 아니다. |
| 추가 학습 | 검증된 예시로 기존 모델의 학습값 일부 또는 전체를 조정하는 작업이다. 대화 기록 저장과는 다르다. |

초기 제품의 ‘전용 AI’는 공개 모델에 HiveDesk의 도구·규칙·자료 전달·검증을 결합한 기능을 뜻한다. 자체 사전학습 모델을 의미하지 않는다.

## 2. 세 등급 모델

### 2-1. 등급은 PC 성능 기준이다

등급 이름은 가칭이며 다른 서비스의 모델명·성능을 의미하지 않는다. 등급은 "이 PC에서 편하게 돌아가는 모델의 크기"를 뜻한다. 아래 PC 사양과 모델 크기는 **예시이며 실측으로 확정**한다(이 문서 작성자는 로컬 모델을 직접 돌려 보지 않았다).

| 등급 | 이런 PC (예시) | 돌릴 모델 | 맡길 수 있는 일 | 속도 안내 |
|---|---|---|---|---|
| Light | 메모리가 적은 노트북, 그래픽 성능 낮음 | 작은 모델 | 분류, 짧은 요약, 대화, 형식 정리 | 짧은 답은 괜찮지만 긴 글은 느릴 수 있음 |
| Standard | 일반적인 최근 PC, 메모리 여유 | 중간 모델 | 문서 초안, 쉬운 코드 수정, 대화 | 일반 업무에 쓸 만한 속도를 목표로 측정 |
| Advanced | 메모리가 넉넉하거나 그래픽 성능 좋은 PC | 큰 모델 | 여러 파일 수정 시도, 긴 문서 | 모델은 크지만 이 PC에서는 감당 가능 |

- 같은 등급이라도 외부 구독 모델(Claude·GPT)보다 어려운 업무에서 실패가 많을 수 있다. 그래서 등급은 **어떤 일을 시도해 볼 수 있는지**의 기준이지 결과 품질의 보증이 아니다.
- 등급은 직원의 직급과 무관하다. 한 PC에서는 한 등급의 모델을 기본으로 쓰고, 사용자가 다른 등급을 직접 고를 수 있다(느리거나 메모리가 부족할 수 있다는 경고와 함께).
- 앱이 **PC를 진단하고 짧은 속도 시험**을 한 뒤 등급을 추천한다. 사양표만으로 정하지 않고 실제로 측정한 속도를 우선한다. (3-1)

### 2-2. 모델과 모드 구분

- 모델: 실제 학습값이 다른 AI. 모델 파일·버전으로 식별한다.
- 모드: 같은 모델의 빠른 응답·충분한 검토 같은 실행 설정이다.
- 첫 버전에서 Standard만 준비됐다면 다른 등급은 ‘준비 중’으로 표시한다. 같은 모델의 이름만 바꿔 서로 다른 능력의 모델인 것처럼 안내하지 않는다.
- 검토 횟수나 처리 시간을 늘리는 것은 품질 향상을 보장하지 않는다. 개선 여부를 평가한다.

### 2-3. 모델 카탈로그

기존 카탈로그에 다음 정보를 확장한다. 실제 타입명은 구현 시 기존 스키마에 맞춘다.

| 정보 | 용도 |
|---|---|
| 모델 ID·버전·원본 출처·파일 해시 | 정확한 설치 대상과 실행 이력 확인 |
| 제품 등급·지원 직무 | 직원 배정과 자동 선택 |
| 도구 호출·이미지 입력 지원 여부 | 업무에 필요한 능력 확인 |
| 다운로드 크기·설치 후 용량 | 설치 전 안내 |
| 검증한 OS·칩·메모리·문맥 설정 | 지원 환경 안내 |
| 라이선스 원문·고지·배포 검토 상태 | 상용 배포 가능 여부 확인 |
| 평가 결과·추천 실행 설정 | 품질 관리와 회귀 확인 |

특정 모델명·용량·최소 RAM·판매 가격은 아직 확정하지 않는다. 후보를 실제 장비에서 평가한 뒤 채운다.

모델은 몇 달 단위로 바뀌므로 추천 모델 목록(카탈로그)은 **앱 업데이트와 분리된 데이터 파일**로 두고, 앱을 새로 배포하지 않아도 갱신할 수 있게 한다. 갱신 파일의 출처를 확인하고, 라이선스 검토를 마치지 않은 모델은 추천 목록에 넣지 않는다.

### 2-4. 기존 등급 체계와 노력 설정

앱에는 이미 모델 등급 세 단계(경량 `light` / 균형 `balanced` / 최상위 `top`)와 이어받기의 "같은 등급 → 한 단계 위" 규칙이 있다. 로컬 모델 등급도 **같은 세 단계에 끼워 넣어** 챗의 모델 선택, 업무 배정, 이어받기가 그대로 동작하게 한다. 이름으로 비유하면 Light ≈ Haiku, Standard ≈ Sonnet, Advanced ≈ Opus의 자리다.

- 자리가 같다는 것이 능력이 같다는 뜻은 아니다. 로컬 Standard는 외부 Sonnet급 모델보다 어려운 일에서 약할 수 있다. 그래서 같은 등급이라는 이유만으로 **자동으로 대체 가능하다고 보지 않고**, 5-4의 적합도와 기대 이익을 통과해야 후보가 된다.
- **노력(생각하는 정도)** 은 모델의 "모드"(2-2)다. 기본은 **중간**이다. 노력 설정을 지원하는 모델에서만 낮음/중간/높음을 보여 주고, 지원하지 않는 모델은 보여 주지 않는다. 높음은 더 오래 걸린다는 경고를 함께 보여 준다.
- 한 PC에서는 보통 한 등급의 모델을 기본으로 쓴다. 큰 모델은 메모리에 함께 올라가지 않거나 바꿀 때 로딩이 오래 걸릴 수 있다.

## 3. 사용자 PC에서 실행

### 3-1. 첫 설치 흐름

1. AI 연결 화면에 ‘HiveDesk AI — 내 PC에서 실행’을 추가한다.
2. OS·칩·메모리·디스크 여유와 지원 실행 장치(그래픽 메모리 포함)를 확인한다. 실제 남은 메모리도 고려한다. 짧은 속도 시험으로 초당 생성 속도를 재고, 그 결과로 **PC 등급(Light / Standard / Advanced)을 추천**한다. 시험이 끝나기 전에는 속도를 단정하지 않는다. PC 사양이 바뀌었거나 이전보다 눈에 띄게 느려지면 속도 시험을 다시 하고 추천을 갱신한다.
3. 설치 가능한 검증 모델, 다운로드 크기, 예상 설치 용량을 보여 준다. 속도는 측정 전 단정하지 않는다.
4. 사용자가 설치를 누르면 실행 엔진과 모델을 준비한다. 모델을 앱 설치 파일에 모두 포함하지 않고 별도 다운로드를 기본으로 한다.
5. 다운로드 재개와 취소를 지원하고 완료 시 무결성을 검사한다.
6. 짧은 응답·도구 요청 시험을 수행한다. 파일 작업 시험은 전용 임시 폴더에서 한다.
7. 성공하면 모델 에이전트를 만들고 직원에게 연결할 수 있게 한다. **같은 시점에 챗의 모델 목록에도 나타나, 설치 직후 바로 대화로 써 볼 수 있다.** (14-5)

지원 장비인지 확인되지 않았거나 시험이 실패하면 ‘연결 완료’로 표시하지 않는다. 실패 이유와 재시도·더 작은 모델 선택을 제공한다.

### 3-2. 설치·업데이트 관리

- 상태: 미설치 → 다운로드 중 → 검증 중 → 준비됨. 실패·업데이트 가능 상태를 별도로 둔다.
- 다운로드는 임시 파일에 저장하고 검증이 끝난 뒤 설치 완료 처리한다.
- 실행 중인 업무는 시작 당시 모델 버전에 고정한다. 업데이트는 해당 실행 종료 후 적용한다.
- 이전 버전을 즉시 지우지 않고 되돌릴 수 있게 하되, 보관 용량을 표시한다.
- 모델 삭제는 사용 중인 직원·실행 영향을 보여 준다. 실행 중에는 삭제하지 않는다.
- 모델 파일은 공용 캐시를 재사용할 수 있지만 회사별 대화·메모리·도구 결과는 분리한다.
- 로컬 실행 엔진은 기본적으로 PC 내부에서만 접근할 수 있게 한다. 엔진 종료가 다른 앱의 작업을 끊지 않도록 소유권을 구분한다.

### 3-3. PC 자원 관리

직원이 20명이어도 모델을 20개 동시에 올리지 않는다. 여러 직원이 같은 모델을 순서대로 사용할 수 있다.

- 초기 로컬 동시 실행 기본값은 1이다. 장비 평가 후 상향할 수 있다.
- 추론 자원 대기와 작업 폴더 잠금을 분리한다. 모델이 비었어도 같은 폴더를 다른 작업이 수정 중이면 시작하지 않는다.
- 메모리 부족은 구독 한도와 구분한다. 같은 설정의 무한 재시도를 막는다.
- 작은 모델로 변경하거나 문맥을 줄이면 결과에 영향이 있으므로 변경 사실을 기록한다. 필수 요구사항·권한 규칙은 자르지 않는다.
- 절전·앱 종료·실행 엔진 충돌 후에는 마지막 안전한 기록에서 재개한다. 이미 수행한 쓰기를 무조건 다시 실행하지 않는다.
- 챗과 업무가 같은 로컬 모델을 함께 쓰면 업무가 먼저 순서를 가진다. 챗은 "업무가 모델을 쓰는 중이라 잠시 기다려요"로 보여 주고, 무한정 막지 않는다. (14-6)

### 3-4. OpenAI 호환 연결 (Ollama·LM Studio 등)

로컬 모델은 **OpenAI 호환 연결 하나**로 붙인다. API 키 기반 유료 서비스 연결은 만들지 않는다.

- 사용자가 내 PC의 로컬 주소(예: Ollama·LM Studio가 여는 주소)를 입력하거나, 앱이 흔한 기본 주소를 찾아 보여 준다. 키는 필요 없다.
- 연결하면 그 주소가 알려 주는 모델 목록을 가져와 모델 에이전트로 만든다. 모델 크기를 알 수 있으면 등급을 함께 표시한다.
- 앱이 모델 설치를 직접 관리하는 기능(3-1, 3-2)은 이 연결이 안정된 뒤의 두 번째 단계다. 처음에는 사용자가 이미 설치한 엔진과 모델을 연결한다.
- 연결이 꺼져 있거나 모델이 없으면 "엔진이 꺼져 있어요", "모델을 먼저 받아 주세요"처럼 이유를 나눠 알려 준다.
- 한도가 없는 대신 PC 한계(속도·메모리·동시 실행·발열)가 있음을 화면에서 알려 준다. 메모리 부족과 외부 구독 한도는 서로 다른 사유로 기록한다.

### 3-5. 내 네트워크의 강한 PC 연결

OpenAI 호환 연결은 주소만 받으므로, 집이나 사무실의 **그래픽 성능이 좋은 다른 PC**에서 엔진을 열고 이 PC에서 그 주소를 입력해도 된다. 클라우드 서버 없이 큰 모델을 쓰는 가장 간단한 방법이다.

- 같은 네트워크 안에서만 열도록 안내하고, 인터넷에 그대로 공개하지 않는다. 간단한 접속 확인(비밀번호 등)을 두는 것을 권한다.
- 연결 화면에는 "이 PC"와 "다른 PC(주소)"를 구분해 표시하고, 상대 PC가 꺼져 있으면 그 이유를 알려 준다.
- 보내는 내용이 다른 PC로 간다는 사실을 처음 연결할 때 한 번 알려 준다.

### 3-6. 사용 팁 (기능 아님)

로컬 모델은 컴퓨터를 쓰지 않을 때, 그리고 전원이 연결돼 있을 때 돌리면 덜 느리고 배터리와 발열을 아낄 수 있다. 앱은 자리 비움 감지나 예약 실행 같은 기능을 따로 만들지 않고, 이 내용을 화면 안내와 사용법 가이드로만 알려 준다.

## 4. 모델이 실제로 일하는 구조

### 4-1. 구성 분리

```text
HiveDesk 화면 / 직원 / 업무 / 승인 / 챗
                 │
            업무 실행 관리자
                 │
       모델 연결 인터페이스
          ┌──────┴──────┐
     로컬 실행 엔진    서버 AI
          └──────┬──────┘
                │ 도구 실행 요청
      PC의 권한 검사·도구 실행기
                │
       파일 읽기·수정·테스트
                │
      실행 결과를 모델에 전달
```

모델 연결은 응답·도구 요청·사용량·오류·취소를 공통 형식으로 반환한다. 공급자별 모든 기능이 같다고 가정하지 않고 지원 능력을 확인한다. 기존 CLI 어댑터는 호환 경로로 유지한다. 챗은 이 모델 연결을 도구 없이(또는 읽기 도구만) 쓰는 가장 단순한 사용처다.

### 4-2. 한 번의 업무 처리

1. 업무·권한·필요 자료를 준비하고 실행 ID와 체크포인트를 만든다.
2. 모델이 응답하거나 도구 실행을 요청한다.
3. 앱이 도구 인자, 허용 경로, 회사 범위, 승인 상태를 검사한다.
4. 허용된 도구를 실행하고 결과를 크기 제한과 함께 모델에 전달한다.
5. 모델이 다음 작업을 판단한다. 완료·질문·승인 대기·취소·예산 초과 시 종료한다.
6. 실제 변경과 테스트 결과를 보고서에 연결하고 기존 사람 확인 절차로 보낸다.

도구 호출이 없다는 이유만으로 업무 성공으로 처리하지 않는다. 약속한 파일이 만들어졌는지, 요구된 테스트가 실행됐는지 확인한다. 모델이 말한 성공과 실제 검증 결과를 구분한다.

### 4-3. 초기 도구와 제한

| 도구 | 첫 구현 범위 |
|---|---|
| 파일 목록·검색·읽기 | 승인된 작업·참고 폴더, 읽기 범위와 크기 제한 |
| 파일 생성·패치 | 승인된 쓰기 폴더, 수정 전 파일 해시 확인 |
| 테스트·명령 실행 | 기존 권한·승인 정책과 OS 수준 실행 제한 적용 |
| 진행·질문·보고 | 기존 업무 상태·타임라인에 연결 |

경로 우회와 심볼릭 링크를 처리하고, 모델 지시만으로 파일 접근을 통제하지 않는다. 명령 실행은 파일 API와 별개로 제한해야 한다. 외부 페이지·문서는 참고 자료로 전달하고 권한을 바꾸는 지시로 취급하지 않는다.

처리 단계 수·총 시간·출력량·같은 도구 오류 반복에 상한을 둔다. 상한 도달 시 남은 일을 기록하고 대기하거나 인계한다. 실행 제한은 사용자 설정과 업무 난이도에 맞춰 조정한다.

### 4-4. 기억과 자료

- 회사 규칙, 현재 업무, 관련 파일·이전 결과만 선별해 전달한다.
- 문맥 예산을 설정하고 필수 규칙·업무 목표·최신 변경 상태를 먼저 보존한다.
- 오래된 기록은 요약하거나 검색으로 찾는다. 요약에는 출처를 남긴다.
- 회사·프로젝트 간 검색 범위를 분리한다. 공유 허가가 없는 다른 회사의 자료는 포함하지 않는다.
- 새 지식을 메모리에 저장하는 것과 모델을 추가 학습하는 것을 구분한다.
- 챗의 대화는 업무 메모리로 자동 저장하지 않는다. 사용자가 고른 내용만 팀 메모리에 남긴다. (14-8)

### 4-5. 로컬 모델은 앱이 이끄는 수정 방식으로

작은 모델은 도구 호출 형식을 틀리거나 같은 호출을 반복하는 일이 많다. 그래서 로컬 모델에는 4-2의 "모델이 도구를 알아서 반복 호출하는" 구조를 기본으로 쓰지 않고, **앱이 일을 이끄는 방식**을 먼저 만든다.

1. 앱이 업무와 관련된 파일을 고른다(경로 힌트, 검색, 프로젝트 요약 활용). 읽기 권한과 크기 제한을 지킨다.
2. 파일 내용과 요청을 모델에 준다. 모델은 **수정된 파일 전체 또는 변경 내용만** 돌려준다.
3. 앱이 권한과 경로를 확인하고 변경을 적용한다(체크포인트를 먼저 만든다).
4. 앱이 자동 검사(테스트·타입 검사 등)를 돌린다. 실패하면 오류를 붙여 같은 모델에게 한두 번 다시 시킨다.
5. 계속 실패하면 외부 모델로 올려 보내거나(5-4) 사람 확인으로 넘긴다. 실패한 내용은 인계 요약에 담는다.

이 방식은 모델이 도구 호출을 잘할 필요가 없고, 이미 있는 자동 검사·체크포인트·되돌리기를 그대로 쓴다. 큰 모델이나 도구 호출이 안정적인 모델에는 4-2의 반복 구조를 쓸 수 있다. 어느 모델에 어느 방식을 쓸지는 실측(8-1) 결과로 정한다.

### 4-6. 로컬용 짧은 프롬프트

로컬 PC에서는 입력이 길수록 첫 응답까지 오래 걸린다. 업무 프롬프트(팀 규칙, 메모리, 프로젝트 요약, 보고 형식)를 그대로 보내지 않고 **로컬용 프롬프트 모양**을 따로 둔다.

- 등급별 문맥 예산을 둔다(Light는 아주 짧게). 필수 규칙·업무 목표·최신 변경 상태를 먼저 담고 나머지는 예산 안에서 고른다.
- 모델을 메모리에 계속 올려 두는 시간(유지 시간)을 정해 업무 사이의 로딩 대기를 줄인다.
- 같은 앞부분이 반복되는 프롬프트는 엔진이 지원하면 앞부분 재사용을 쓴다. 지원 여부는 실측으로 확인한다.

## 5. 자동 선택과 v5 이어받기 연계

### 5-1. 선택 순서

1. 같은 회사, 필요한 도구·권한·업무 능력, 실행 위치 허용 여부를 먼저 검사한다.
2. 사용자가 등급을 고정했다면 그 범위에서 선택한다.
3. 자동 모드에서는 평가 이력과 업무 종류를 기준으로 적합한 모델을 고른다. 초기에는 단순한 규칙으로 시작한다.
4. 구독 한도·PC 자원·서버 대기열·예산을 확인한 뒤 실행한다.

직원의 직급과 모델 등급은 서로 다른 값이다. 관리자가 반드시 Advanced를 쓰거나 낮은 직급이 반드시 Light를 쓰도록 고정하지 않는다. 로컬 모델의 등급은 이 PC의 성능으로 정해지므로, 업무를 로컬로 보낼지는 **그 PC의 등급이 감당하는 일인지**를 기준으로 판단한다. 챗에서는 자동 선택 없이 사용자가 고른 모델을 그대로 쓴다. (14-5)

### 5-2. 이어받기

v5의 동급 → 상위 직원 후보 탐색을 활용하되, 후보가 사용하는 모델의 능력·위치·예산 조건을 추가한다. v5 구현 완료 여부는 별도로 확인하고 연동한다.

> 참고(2026-10-19 확인): v5의 한도 이어받기·작업 현황은 v0.5.0에 구현·릴리스됐다. 자동 테스트는 통과했고 실제 AI 연결로의 검증은 아직 남아 있다(`docs/real-ai-checklist.md`).

- 외부 CLI가 한도에 걸리면 적격 로컬 직원도 후보에 넣는다.
- 로컬 모델이 필요한 도구나 품질 기준을 충족하지 못하면 강제로 넘기지 않는다.
- 로컬 메모리 부족, 서버 용량 대기, 외부 계정 한도는 서로 다른 사유로 기록한다.
- 후보를 반복 방문하지 않으며 업무당 인계 횟수에 상한을 둔다.
- 자동 서버 전환은 사용자가 허용한 전송 범위·비용 한도 안에서만 가능하다. 처음부터 자동 허용하지 않는다.
- 같은 모델·버전의 직원이 교차 검토하면 ‘다른 모델 검토’로 계산하지 않는다. 독립 모델 검토 규칙을 충족하지 못하면 다른 후보나 사람 확인으로 보낸다.

### 5-3. 인계 자료

목표, 완료 항목, 남은 항목, 바뀐 파일, 실행한 테스트, 실패 이유, 승인 상태, 체크포인트와 실행 ID를 전달한다. 가능하면 실행 기록에서 프로그램으로 구성해 추가 AI 호출을 줄인다.

요약 목표는 1천 토큰 안팎으로 두되 필수 상태를 누락하지 않는다. 큰 diff는 전문을 무조건 붙이지 않고 참조와 필요한 부분을 전달한다. 서로 다른 모델 간 비공개 추론이나 내부 세션 상태의 호환을 가정하지 않는다.

### 5-4. 로컬 대체 판단 (기대 이익)

대체할 수 있으면 대체하는 것이 한도를 아끼는 이 기능의 목적에 맞다. 다만 로컬을 무조건 동급으로 보지 않고, **후보로 넣고 이익과 비용을 따져 고른다.**

```text
기대 이익 = 성공 확률 × (한도 절약 + 기다림 회피)
          − 실패 확률 × (낭비한 시간 + 다시 하는 비용)
```

- **성공 확률**은 추측하지 않고 기존 적성 기록(모델·직무별 첫 통과율)으로 정한다. 로컬 모델은 낮은 값으로 시작하고, 실제 통과가 쌓일수록 올라간다. 기록이 충분하지 않으면 "아직 모름"으로 보고 쉬운 일에만 쓴다.
- **시간 비용**은 3-1에서 잰 속도로 예상 시간을 계산하고, 외부 모델이 한도로 기다려야 하는 시간과 비교한다. 한도가 곧 풀리면 기다리는 쪽을 택할 수 있다.
- **실패 비용을 낮추는 장치**를 함께 본다: 자동 검사로 결과를 바로 확인할 수 있는 일, 작고 안전한 변경(민감한 파일 제외), 체크포인트로 되돌릴 수 있는 일을 우선 후보로 한다.
- 로컬이 자동 검사에서 연속으로 실패하면(기본 2번) 외부 모델로 올려 보내고, 실패 내용을 인계 요약에 담는다.
- **교차 검토의 독립 모델 규칙은 그대로** 지킨다. 로컬 모델이 외부 모델의 결과를 보는 것은 두 번째 확인으로 쓸 수 있지만, 위험한 변경의 단독 검토자는 아니다.

**사용자가 정하는 범위**: 로컬 사용 범위를 `끔` / `쉬운 일만` / `검사로 확인되는 일까지` / `적극적` 중에서 고른다. 기본은 `쉬운 일만`이다. 로컬로 보낼 때는 이유와 예상을 보여 준다(예: "한도 대기 55분 → 내 PC로 진행, 약 12분 예상"). 예상 시간이 길면 한 번 확인을 받는다.

**절약 효과 표시**: 로컬로 처리해서 외부 모델 실행을 몇 번 아꼈는지 보여 준다. 이 숫자가 로컬 기능의 가치를 확인하는 기준이다.

## 6. 서버 확장과 많은 사용자 지원

### 6-1. 먼저 옮길 것

초기 서버 버전은 AI 계산만 서버에서 한다. 사용자 PC의 파일 읽기·수정·테스트는 HiveDesk가 계속 수행한다. 프로젝트 전체를 서버에서 실행하는 기능은 별도 후속 범위다.

```text
사용자 PC → 인증된 요청 → 계정·회사 확인 → 예산 확인 → 대기열
                                                        ↓
                                                 등급별 모델 실행
                                                        ↓
사용자 PC ← 응답 / 도구 요청 ← 스트리밍 연결 ← 결과
```

서버는 임의의 로컬 경로를 직접 열 수 없다. 도구 요청을 받은 PC가 권한을 검사한다. PC가 꺼지면 로컬 작업이 필요한 업무는 진행되지 않고 대기 상태가 된다.

### 6-2. 계정과 자료 분리

- 사용자 인증과 회사별 멤버 권한을 확인한다. 요청에 적힌 회사 ID만 믿지 않는다.
- 대화·첨부·검색 자료·캐시·로그는 계정/회사 경계를 지킨다. 모델의 공용 학습값과 사용자별 실행 상태는 구분한다.
- 직원 프로필에 서버 비밀 키를 넣지 않는다. 앱 세션 인증과 서버 운영 자격증명을 분리한다.
- 서버에 보내는 자료 종류와 전송 범위를 실행 전 확인할 수 있게 한다.
- 전송 암호화, 보관 기간, 삭제 처리, 접근 기록을 구현한다. 보관 기간은 출시 전 확정한다.
- 사용자 자료를 모델 학습에 사용하는 기능은 기본적으로 꺼 두고, 별도 동의와 삭제 정책이 준비되기 전에는 수집하지 않는다.

### 6-3. 부하와 공정성

- 가입자 수와 동시 실행 수를 구분한다. 실제 용량은 같은 시간에 어떤 모델로 얼마나 긴 업무를 실행하는지에 달려 있다.
- 계정별 동시 실행 수·대기 업무 수·처리 예산을 제한한다. 한 사용자가 전체 자원을 독점하지 못하게 한다.
- Light / Standard / Advanced의 대기열과 자원 배분을 관리하되 초기 서버는 적은 모델로 시작한다.
- 여유가 없으면 대기 순서를 표시한다. 등급을 조용히 낮추거나 무조건 실패 처리하지 않는다.
- 취소된 요청은 대기열과 모델 실행에 전파하고 실제 중단 여부를 확인한다.
- 첫 응답 시간, 전체 완료 시간, 성공률, 처리량, 최대 메모리, 업무당 비용을 측정한다.
- 챗은 짧은 요청이 많고 응답 속도를 바로 체감한다. 서버에서는 챗 요청과 긴 업무를 같은 대기열에 섞지 않고, 챗의 첫 응답 시간을 따로 측정한다.

개발 완료 전에 소규모 서버 시험을 한다. 반복 가능한 업무 묶음으로 동시 요청을 늘리며 지연과 오류를 측정한 뒤 지원 규모와 요금제를 정한다.

### 6-4. 연결 끊김과 중복 실행

실행·도구 요청마다 고유 ID를 부여하고 처리 상태를 저장한다. 재접속하면 새 업무를 만드는 대신 기존 실행 상태를 조회한다.

파일 수정과 외부 쓰기는 무조건 재시도하지 않는다. 요청 수신 → 실행 시작 → 결과 기록 상태와 실제 파일 해시·외부 응답을 확인한다. 실행 후 기록 전에 끊겨 완료 여부가 불명확하면 사람이 확인할 수 있는 상태로 둔다.

## 7. 화면과 기본 설정

### 7-1. AI 연결 화면

- 내 PC AI / 서버 AI / 기존 CLI 연결을 구분한다.
- 등급별 설치 여부·실행 가능 여부·현재 버전·지원 업무를 보여 준다.
- 로컬은 다운로드·업데이트·삭제, 서버는 로그인·연결 상태·사용량을 보여 준다.
- 미지원 장비, 모델 미설치, 메모리 부족, 서버 대기를 각각 설명한다.
- 각 모델 줄에 **"챗으로 써 보기"** 버튼을 둔다. 누르면 그 모델이 선택된 새 대화가 열린다. (14장)

### 7-2. 업무 화면과 말풍선

업무에는 직원, 모델 등급, 실제 모델 버전, 실행 위치, 선택 이유를 기록한다. 기본 화면은 ‘Standard · 내 PC’처럼 간단히 보여 주고 상세에서 기술 정보를 확인한다.

v5 말풍선은 기존 도구 이벤트로 생성한다. ‘AI 준비 중’, ‘PC 메모리 대기’, ‘서버 순서 대기’, ‘다른 모델이 이어받는 중’을 추가한다. 말풍선 생성에 별도 모델을 호출하지 않는다.

업무 상세와 사용량 화면에는 로컬로 처리한 업무 수, 아낀 외부 모델 실행 횟수, 로컬 업무의 평균 시간과 통과율을 보여 준다. (5-4)

## 8. 상업화와 품질

### 8-1. 판매 대상

HiveDesk의 업무 배정, 자료 연결, 작업 도구, 승인, 되돌리기, 검증, 팀 관리와 모델 실행 경험을 제품으로 제공한다. 공개 모델을 활용했다는 사실과 출처를 정확하게 표시한다.

- 로컬 상품: 앱 기능·업데이트·지원 등의 대가를 받는 방식을 검토한다. 공급자 API 추론 비용이 없더라도 배포·지원·업데이트 운영비는 남는다.
- 서버 상품: 포함 사용량 또는 사용량 기반 요금을 검토한다. 실측 원가 없이 ‘무제한’을 약속하지 않는다.
- 기존 외부 CLI 계정 연결과 HiveDesk 서버 사용량을 분리해 보여 준다. 개인 구독 연결을 서버 재판매의 근거로 삼지 않고 공급자 조건을 별도로 검토한다.

### 8-2. 배포 전 확인

모델의 정확한 버전과 실행 엔진에 대해 상업 이용, 재배포, 변경, 고지 조건을 확인한다. 앱·모델·학습 데이터의 조건을 각각 관리한다. 공개 다운로드 가능 여부만으로 상업 배포를 판단하지 않는다.

### 8-3. 평가와 추가 학습

첫 단계는 추가 학습 없이 도구와 자료 전달을 개선한다. 반복적으로 나타나는 부족함을 평가로 확인한 뒤 추가 학습을 검토한다.

- 한국어 문서·분류, 작은 코드 수정, 여러 파일 오류 수정, 도구 사용, 승인 준수 등 평가 업무를 만든다.
- 동일 업무에서 완료율, 테스트 통과, 잘못된 파일 변경, 시간, 자원 사용량을 비교한다.
- 정답이나 평가 업무를 학습 자료에 섞지 않는다.
- 학습 자료는 사용 권한이 있고 사람이 검증한 예시만 사용한다.
- 추가 학습 후 기존 능력이 나빠지지 않았는지 평가하고 이전 버전으로 되돌릴 수 있게 한다.

8-7은 전체 개발 완료를 기다리지 않고 8-4 이후 병행 가능한 시험 범위로 시작한다. 서버 정식 출시는 로컬 검증과 원가 측정 이후다. 개발 토큰·기간은 구현 범위와 모델 시험에 따라 달라 근거 없는 총량을 제시하지 않는다.

챗-1은 로컬 모델이나 서버 없이 지금의 연결만으로 만들 수 있어서 v6의 위험(모델 선정·라이선스·원가)과 무관하게 먼저 제공할 수 있다. 그리고 8-2의 로컬 모델 설치가 끝나면 챗이 가장 먼저 써 보는 자리가 된다.

## 11. 테스트 계획

- 설치: 다운로드 중단·재개, 디스크 부족, 손상된 파일, 버전 되돌리기, 사용 중 삭제 차단.
- 실행: 응답만 하는 모델, 정상 도구 호출, 잘못된 인자, 반복 실패, 문맥 초과, 취소, 엔진 충돌.
- 권한: 폴더 밖 접근, 심볼릭 링크 우회, 승인 전 쓰기, 셸을 통한 우회, 외부 자료의 지시 주입.
- 정확성: 보고 내용과 실제 파일 변경·테스트 실행의 일치, 실패를 성공으로 표시하지 않기.
- 인계: 구독 한도→적격 로컬, 부적격 후보 제외, 권한 유지, 상한·순환 차단, 체크포인트 유지.
- 자원: 여러 직원의 단일 모델 공유, 동시 실행 제한, 메모리 부족 후 무한 재시도 방지, 폴더 잠금.
- 서버: 다른 계정·회사 자료 접근 차단, 대기열 공정성, 예산 초과, 취소·재접속·중복 요청.
- 장애: 파일 수정 직후 연결 단절, 완료 기록 전 종료, 불명확한 작업 재실행 방지.
- 화면: 모델 미설치·지원 불가·대기·취소·전환 표시, 전송 범위와 실행 위치 표시.
- 실제 장비: 지원 예정 PC별 첫 응답·전체 업무 시간·최대 메모리·품질 측정.
- 로컬 연결은 모의 응답으로 상태·오류 처리를 자동 시험하고, **실제 로컬 모델은 CI에서 돌릴 수 없으므로** 직접 PC에서 도는 점검 목록(`docs/real-ai-checklist.md`)으로 나눈다.
- 앱이 이끄는 수정(4-5): 적용 전 체크포인트, 검사 실패 시 재시도 상한, 연속 실패 시 올려 보내기, 인계 요약 내용.
- 대체 판단(5-4): 성공 확률이 낮을 때 로컬로 보내지 않기, 한도가 곧 풀릴 때 기다리기, 사용 범위 설정 반영, 이유 표시, 독립 모델 규칙 유지.
- 챗: 14-12.

모의 응답 테스트는 상태와 오류 처리를 검증하고, 실제 모델 테스트는 업무 수행 능력을 검증한다. 둘 중 하나만 통과한 것을 전체 완료로 보지 않는다.

## 14. 기본 AI 챗

### 14-1. 무엇이고 왜 필요한가

지금 HiveDesk는 **일을 맡기는** 앱이다. 일에는 보고서·검토·승인·되돌리기가 따라붙어서, "이 에러가 무슨 뜻이야?", "이 문장 다듬어 줘", "이 폴더 구조 설명해 줘" 같은 가벼운 질문에는 무겁다. 그래서 모델을 골라 바로 대화하는 **기본 AI 챗**을 더한다.

- 챗은 **대화**다. 파일을 바꾸지 않는다. 바꿔야 하면 업무로 넘긴다. (14-7)
- 직원을 만들지 않아도 쓴다. 직원은 업무용 자리이고, 챗은 모델만 고르면 된다.
- 처음에는 지금 연결된 CLI(Claude·Codex·Antigravity)로 만든다. v6의 내 PC AI·서버 AI는 같은 챗의 모델 목록에 나중에 더해진다.

### 14-2. 지금 코드로 가능한 이유

확인한 코드(`adapters.ts`, `runner.ts`) 기준이다. 실제 CLI로 대화를 이어 가는 것은 아직 시험하지 않았다.

| 필요한 것 | 지금 있는 것 |
|---|---|
| 대화 이어 가기 | Claude는 세션을 이어 가는 방식(`resume: 'session'`), Codex·Antigravity는 이전 대화를 프롬프트에 다시 담는 방식(`resume: 'replay'`)이 업무 쪽에 이미 있음 |
| 모델 고르기 | 어댑터마다 모델 지정 옵션(`modelFlag`)과 카탈로그·모델 에이전트 목록이 있음 |
| 읽기 전용 | Claude·Codex는 권한을 CLI가 강제함. Antigravity는 프롬프트 안내만 |
| 응답 표시 | 스트림 출력 파서와 실시간 활동 이벤트가 있음 |
| 한도 감지 | 연결 단위 한도 기록과 감지 규칙이 있음 |

새로 만들 것: 대화 저장, 챗 전용 짧은 프롬프트, 챗 화면, 업무와 오가는 기능.

### 14-3. 화면

사이드바 "일" 그룹에 **챗** 메뉴를 둔다(기본 모드에서도 보임).

```text
┌ 대화 목록 ──────┬ 대화 ─────────────────────────────────────┐
│ + 새 대화        │ [모델: Claude Sonnet 5.5 ▾]  [📂 폴더 참고]  │
│ 오늘             │                                            │
│  에러 메시지 질문 │  나:  이 에러가 무슨 뜻이야? …              │
│  README 다듬기   │  AI:  …(글자가 나오는 대로 표시)            │
│ 어제             │                                            │
│  …              │  ── 여기서 모델을 GPT로 바꿨어요 ──          │
│                  │                                            │
│                  │ [메시지 입력…                  ] [보내기/중지]│
└──────────────────┴────────────────────────────────────────────┘
```

- **모델 선택**: 위쪽 드롭다운. 연결 확인이 끝난 모델만 나오고 등급(가벼움/균형/강함)과 위치(CLI·내 PC·서버)를 함께 보여 준다. 대화 도중에도 바꿀 수 있고, 바꾼 자리에 표시선이 남는다.
- **새 대화 / 목록**: 제목은 첫 질문의 앞 40자로 앱이 붙인다(AI 호출 없음). 이름 바꾸기·삭제·마크다운 내보내기.
- **보내기 / 중지**: 응답 중에는 중지 버튼. 중지하면 그때까지 나온 글을 남긴다.
- **폴더 참고**: 폴더를 고르면 그 폴더를 읽기 전용으로 참고해 질문에 답한다.
- 모델이 하나도 연결돼 있지 않으면 "AI 연결에서 로그인부터 해 주세요" 안내와 이동 버튼을 보여 준다.

### 14-4. 한 번 주고받는 흐름

1. 사용자가 보낸다. 앱이 메시지를 저장하고 응답 칸을 만든다.
2. 앱이 **챗 전용 프롬프트**를 만든다. 짧은 역할 안내와 대화 기록만 넣는다. 업무용 보고 형식, 계획 표시(`[[PLAN]]`), 팀 메모리, 프로젝트 요약은 넣지 않는다.
3. 모델 연결로 한 번 실행한다. 작업 폴더는 챗 전용 빈 폴더(`<작업 공간>/chat`)이고 권한은 읽기다. 폴더를 참고로 붙였으면 그 폴더만 읽기 전용 참고로 전달한다.
4. 출력이 오는 대로 화면에 표시하고, 끝나면 응답과 사용량(알 수 있는 만큼)을 저장한다.
5. 이어 가기: Claude는 세션을 이어 간다. 다른 모델로 바꾸었거나 세션을 이을 수 없는 CLI는 이전 대화를 프롬프트에 다시 담는다(최근 대화부터 글자 수 한도까지, 오래된 부분은 "앞부분 생략"으로 표시).

### 14-5. 모델 선택

- 목록의 출처는 연결 화면의 **모델 에이전트**(사용할 수 없다고 확인된 것은 제외)다. 직원을 만들 필요가 없다.
- 기본값: 마지막에 쓴 모델. 처음에는 사용 가능한 가장 가벼운 모델(한도를 아끼기 위해).
- 챗에서는 자동 선택을 하지 않는다. 사용자가 고른 모델을 그대로 쓴다. 업무의 자동 배정·이어받기와 섞지 않는다.
- v6가 들어오면 "내 PC"와 "서버" 모델이 같은 목록에 위치 표시와 함께 더해진다. 서버 모델을 고르면 대화 내용이 서버로 간다는 사실과 전송 범위를 대화 위쪽에 보여 준다.
- 읽기를 강제하지 못하는 CLI(현재 Antigravity)는 목록에 작은 안내를 단다: "파일을 바꾸지 않도록 안내만 해요". 그 모델의 챗도 빈 챗 폴더에서 실행해 영향 범위를 줄인다.

### 14-6. 한도·자원·비용

- 챗의 한 번 주고받기도 **연결의 사용량**에 든다. 실행 횟수 집계에서 '챗'으로 구분해서, 업무의 예상 실행 횟수와 적성 기록을 부풀리지 않는다(v5 7-1에서 한도 실행을 제외한 방식과 같다).
- 한도에 걸리면 자동으로 다른 모델로 바꾸지 않는다. "이 모델은 한도예요. 다른 모델로 이어서 보낼까요?"와 모델 선택 버튼을 보여 준다. 사용량 가중치가 크게 오르는 선택(v5의 확인 배수)은 한 번 더 묻는다.
- 동시 실행: 챗은 작업 폴더 잠금과 업무의 최대 동시 실행 수에 포함하지 않는다. 대신 연결당 동시 챗 1건, 앱 전체 2건으로 제한한다. 업무와 같은 로컬 모델을 쓸 때는 업무가 먼저다(3-3).
- 대화가 길어져 한도가 가까우면 "새 대화로 이어 갈까요?"를 제안한다. 이어 가기는 앱이 만든 대화 요점 목록(사용자 질문과 결론)을 새 대화의 첫 맥락으로 넣는다. AI 요약은 선택 사항이다.

### 14-7. 챗과 업무 오가기 (챗-2)

챗은 파일을 바꾸지 않는다. 바꿔야 할 때 업무로 넘기고, 업무 결과에 대해서는 챗으로 묻는다.

1. **이 대화로 업무 만들기**: 앱이 마지막 요청과 결정 사항을 모아 제목·설명 초안을 만든다(사용자 메시지 중심, AI 호출 없음). 사용자가 고쳐서 "맡기기"를 누르면 기존 업무 생성(담당 자동 배정 포함)으로 이어진다. 자동으로 맡기지 않는다.
2. **이 업무에 대해 물어보기**: 업무 상세에서 누르면 그 업무의 보고서·바뀐 파일 목록·자동 검사 결과를 첫 맥락으로 붙인 새 챗이 열린다(읽기 전용, 파일 내용은 사용자가 고른 것만).
3. **챗에서 업무 제안**: 메시지가 일을 시키는 말이면(기존 입력 분류기 사용) "업무로 맡길까요?" 버튼을 보여 준다. 누르기 전에는 아무것도 실행하지 않는다.
4. **팀 메모리에 남기기**: 대화의 한 메시지를 골라 팀 메모리에 저장하는 버튼. 대화는 자동으로 메모리에 들어가지 않는다.

### 14-8. 저장과 개인정보

- 대화는 **이 컴퓨터에만** 저장한다(`.local/chats`). 팀 동기화(git) 대상이 아니다.
- 회사별로 분리한다. 회사를 바꾸면 그 회사의 대화만 보인다.
- 삭제하면 파일도 지운다. 내보내기는 마크다운.
- 서버 모델을 쓴 대화는 그 사실을 대화에 기록하고 전송 범위를 보여 준다. 서버에서의 보관 기간·삭제는 6-2의 정책을 따른다.
- 대화를 모델 학습에 쓰지 않는다(기본 꺼짐, 별도 동의 전에는 수집하지 않는다).

### 14-9. 데이터 모델

```ts
interface Chat {
  id: string
  companyId: string
  title: string
  createdAt: string
  updatedAt: string
  /** 지금 선택된 모델. 위치는 기존 CLI, 내 PC, 서버. */
  model: { adapter: AdapterId | 'local' | 'server'; modelId: string }
  /** Claude 세션 이어 가기용 (모델을 바꾸면 비움) */
  sessionId?: string
  /** 읽기 전용으로 참고하는 폴더 */
  folderRefs: string[]
  /** 업무 상세에서 연 챗이면 그 업무 */
  aboutTask?: string
  messages: ChatMessage[]
}

interface ChatMessage {
  id: string
  role: 'user' | 'assistant' | 'system'   // system: 모델 바뀜, 앞부분 생략 같은 표시
  text: string
  at: string
  model?: { adapter: string; modelId: string }
  status: 'done' | 'streaming' | 'stopped' | 'failed' | 'limit'
  /** 알 수 있는 사용량 (알 수 없으면 비움) */
  usage?: { ms: number; tokens?: number }
}
```

엔진 메서드(제안): `chatList`, `chatCreate`, `chatSend`, `chatStop`, `chatSetModel`, `chatRename`, `chatDelete`, `chatExport`, `chatToTask`, `askAboutTask`. 화면 갱신은 기존 활동 이벤트처럼 `chat` 이벤트로 보낸다.

### 14-10. 구현 위치

| `src/main/index.ts`, `src/preload/index.ts` | IPC |

### 14-11. 단계와 완료 기준

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| 챗-1 | 저장·모델 선택·여러 번 주고받기·스트리밍·중지·삭제·내보내기·한도 안내·폴더 참고 | 연결된 모델로 대화가 이어지고, 모델을 바꿔도 맥락이 유지되며, 파일이 바뀌지 않음 |
| 챗-2 | 대화 → 업무, 업무 → 챗, 업무 제안, 팀 메모리 저장 | 대화에서 만든 업무가 정상 생성되고, 업무 결과를 읽기 전용으로 질문할 수 있음 |
| 챗-3 | 내 PC·서버 모델 추가, 위치·전송 범위 표시 | 같은 화면에서 위치를 고르고, 서버 모델 사용 시 전송 사실이 보임 |

### 14-12. 챗 테스트 계획

- 여러 번 주고받기: 모의 실행기로 기록이 순서대로 쌓이고 두 번째 질문에 앞 대화가 전달되는지.
- 모델 바꾸기: 바꾼 자리에 표시가 남고, 세션을 비운 뒤 이전 대화가 프롬프트에 다시 담기는지.
- 길이 자르기: 한도를 넘으면 오래된 부분이 잘리고 "앞부분 생략"이 표시되는지. 최신 질문은 절대 잘리지 않는지.
- 중지: 응답 중 중지하면 실행이 끝나고 그때까지의 글이 `stopped`로 남는지.
- 한도: 한도 응답 시 `limit` 상태와 안내가 나오고 **자동으로 다른 모델로 바뀌지 않는지**. 가중치가 크게 오르는 선택은 확인을 묻는지.
- 파일 안전: 챗 실행의 작업 폴더가 챗 전용 폴더이고 권한이 읽기인지. 읽기를 강제하지 못하는 CLI는 화면에 안내가 나오는지.
- 집계: 챗 실행이 업무의 예상 실행 횟수·적성 기록에 들어가지 않는지.
- 동시 실행: 연결당 1건·전체 2건 제한, 업무 동시 실행 수에 영향이 없는지.
- 회사 분리·삭제: 회사를 바꾸면 다른 회사 대화가 안 보이고, 삭제하면 파일이 지워지는지.
- 업무 연결(챗-2): 업무 초안이 마지막 요청을 담는지, 자동으로 맡겨지지 않는지, 업무 상세의 챗이 읽기 전용인지.
- 화면: 모델 없음 안내, 응답 중 표시, 모델 바뀜 표시선, 한도 안내 버튼.
- 실제 CLI: 모의 응답 테스트와 별개로 연결된 CLI에서 대화 이어 가기를 직접 확인한다(`docs/real-ai-checklist.md`에 추가).
